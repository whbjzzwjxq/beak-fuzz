# beak-fuzz Quick Start

Minimal setup and run guide for the current OpenVM backend.

For architecture details, see `docs/ARCHITECTURE.md`. For obligation coverage
work, start with `docs/OBLIGATION_IMPLEMENTATION_CONTRACT.md` and track status
in `docs/OBLIGATION_IMPLEMENTATION_MATRIX.md`.

## 1) Environment Setup

### Python side (`beak-py`)

Required:

- `python3`
- `uv`
- `make`

Quick check:

```bash
python3 --version
uv --version
make --version
```

### Rust side

Required:

- `rustup`
- `cargo`

Quick check:

```bash
rustup --version
cargo --version
```

Notes:

- `crates/beak-core` is typically built with stable.
- OpenVM snapshot projects pin their own toolchain via `rust-toolchain.toml`.
- On first build, `cargo`/`rustup` may download toolchains and git dependencies.

## 2) Install OpenVM Snapshot

From repo root:

```bash
make openvm-install COMMIT=bmk-regzero
```

`COMMIT` can be:

- an alias (for example `bmk-regzero`), or
- a full OpenVM commit SHA.

## 3) Run Minimal Example (`openvm-example-x0`)

This runs a tiny `beak-trace` example that checks x0 behavior.

```bash
make openvm-example-x0
```

Equivalent explicit command:

```bash
make openvm-run COMMIT=bmk-regzero BIN=beak-trace ARGS='--bin "12345017 00000533"'
```

## 4) Run Minimal Fuzz (10 iterations)

### Prepare initial seeds (if needed)

If `storage/fuzzing_seeds/initial.jsonl` does not exist yet:

```bash
make extract-initial-seeds
```

### Run loop1 for 10 iterations

```bash
make openvm-fuzz \
  COMMIT=bmk-regzero \
  ITERS=10 \
  INITIAL_LIMIT=1 \
  MAX_INSTRUCTIONS=32 \
  FAST_TEST=1
```

Notes:

- The fuzz target is run in release mode by default (`cargo run --release -q --bin beak-fuzz`).
- `FAST_TEST=1` enables fast insecure parameters for local fuzz/debug.
- `ITERS` maps to `--mutation-iters`: after evaluating the initial JSONL seeds, the runner selects retained corpus entries, applies ISA-aware mutation arms, executes the mutated input, and keeps it only when it discovers a new semantic signature.
- Outputs are written to `storage/fuzzing_seeds/` as:
  - `benchmark-...-corpus.jsonl`
  - `benchmark-...-bugs.jsonl`
  - `benchmark-...-runs.jsonl`

## 5) Full Campaign

The full multi-VM campaign uses one entrypoint from the repository root:

```bash
scripts/run_serial_install_injection.py
```

It installs each configured target when needed, runs the benchmark/injection
workload, and writes:

- `out/serial-install-injection/summary.tsv`
- `out/serial-install-injection/artifacts.tsv`
- `out/serial-install-injection/summary.json`

`summary.json` is generated by the Python runner itself from the TSV/log/artifact outputs; there is no separate campaign profiler script. The two legacy SP1 targets, `sp1-3561f006` and `sp1-fb38df2c`, remain classified separately in the JSON summary because they run bespoke scenarios rather than the generic RV32 benchmark loop.

The campaign seed source is `storage/fuzzing_seeds/initial.jsonl`. That file is
the benchmark corpus used for full experiments. `replay_seed.jsonl` is only a
ground-truth / regression replay manifest for previously confirmed cases; do
not use it as the full-campaign seed corpus.

If `initial.jsonl` is missing, create it first:

```bash
make extract-initial-seeds
```

The campaign does not set a per-eval or per-step timeout, because each semantic step/variant can have VM-specific runtime. The outer per-target budget still defaults to 4 hours (`SOFT_TIMEOUT_SECONDS=14400`).

Recommended full mutation campaign shape is one runner process with built-in VM-level parallelism. By default, the runner treats `CPU_SET` as the total CPU pool, assigns `VM_CORES=32` cores to each VM target, and sets `PARALLEL_VMS=floor(len(CPU_SET) / VM_CORES)` with a minimum of 1. If snapshots are already installed, pass `--skip-install`.

### Fresh-machine smoke campaign

Use this first on a new machine or Docker image. It performs the same install
and run path as the full campaign, but gives each VM commit only a short outer
budget and evaluates one initial seed with one semantic trial. This is intended
to validate toolchains, snapshot installation, project wiring, process cleanup,
and JSONL artifact generation; it is not a coverage or bug-count experiment.

```bash
CPU_SET=0-7 \
VM_CORES=2 \
PARALLEL_VMS=1 \
RUN_ROOT=out/mutation-campaign/smoke \
SOFT_TIMEOUT_SECONDS=120 \
KILL_GRACE_SECONDS=10 \
INITIAL_LIMIT=1 \
MUTATION_ITERS=0 \
MAX_INSTRUCTIONS=64 \
SEMANTIC_WINDOW_BEFORE=0 \
SEMANTIC_WINDOW_AFTER=0 \
SEMANTIC_MAX_TRIALS=1 \
FAST_TEST=1 \
python3 scripts/run_serial_install_injection.py
```

If snapshots are already installed and you only want to re-run the benchmark
portion, add `--skip-install`.

### Full mutation campaign

Full campaign with the default CPU pool and default 32 cores per VM:

```bash
RUN_ROOT=out/mutation-campaign/full \
SOFT_TIMEOUT_SECONDS=1800 \
KILL_GRACE_SECONDS=30 \
MUTATION_ITERS=1000000 \
MAX_INSTRUCTIONS=256 \
SEMANTIC_MAX_TRIALS=64 \
FAST_TEST=1 \
python3 scripts/run_serial_install_injection.py
```

To override the resource model explicitly:

```bash
CPU_SET=0-127 \
VM_CORES=32 \
PARALLEL_VMS=4 \
RUN_ROOT=out/mutation-campaign/full \
SOFT_TIMEOUT_SECONDS=1800 \
KILL_GRACE_SECONDS=30 \
MUTATION_ITERS=1000000 \
MAX_INSTRUCTIONS=256 \
SEMANTIC_MAX_TRIALS=64 \
FAST_TEST=1 \
python3 scripts/run_serial_install_injection.py
```

For repeated runs on a machine where all snapshots are already installed, add
`--skip-install` to either full-campaign command.

`THREADS` is kept as a legacy alias for `VM_CORES` when `VM_CORES` is unset. `PARALLEL_VMS` must fit inside `CPU_SET` without overlapping CPU allocations. The runner reads `storage/fuzzing_seeds/initial.jsonl` by default, applies mutation iterations through `MUTATION_ITERS` / `ITERS`, writes summaries under `RUN_ROOT`, and records campaign artifacts in `storage/fuzzing_seeds/`. It cleans up child process groups on timeout or runner termination. Reported `bugs.jsonl` entries filter out expected injection rejections and invalid/unsupported exception surfaces; rejected runs remain visible in `runs.jsonl`.

Outputs to check after either smoke or full campaign:

```bash
column -t -s $'\t' out/mutation-campaign/smoke/summary.tsv
cat out/mutation-campaign/smoke/summary.json
```

For full runs, replace `smoke` with `full` in those paths.

Useful filters:

```bash
scripts/run_serial_install_injection.py --only-commit 7f643da1
scripts/run_serial_install_injection.py --exclude-commit fb38df2c
scripts/run_serial_install_injection.py --print-commands
```

RISC0 snapshots are cloned from the upstream RISC0 repository by default. To install from a local mirror instead, pass a repo-root-relative path:

```bash
make risc0-install \
  RISC0_COMMIT=c0db0713671c8ec467b3efc26b22a0b0591897ff \
  RISC0_ZKVM_SRC=beak-py/risc0-src
```

## 6) Pico Audit Workflow (45e74 commit)

Pico audit commit from CSV:

- `45e74ccd62758c6d67239913956e749adaba261c`

This workflow is managed from `beak/`, with project-local binaries under:

- `projects/pico-45e74ccd62758c6d67239913956e749adaba261c/`

Install snapshot:

```bash
make pico-install PICO_COMMIT=45e74ccd62758c6d67239913956e749adaba261c
```

Pico source snapshot path (same style as OpenVM under `beak-py/out`):

- `beak-py/out/pico-45e74ccd62758c6d67239913956e749adaba261c/pico-src`

Build project binaries:

```bash
make pico-build PICO_COMMIT=45e74ccd62758c6d67239913956e749adaba261c
```

Run full workflow (single entry, OpenVM-style):

```bash
make pico-fuzz PICO_COMMIT=45e74ccd62758c6d67239913956e749adaba261c PICO_ITERS=1000
```

Run with chained direct injection enabled:

```bash
make pico-fuzz \
  PICO_COMMIT=45e74ccd62758c6d67239913956e749adaba261c \
  PICO_ITERS=1000 \
  PICO_CHAIN_DIRECT_INJECTION=1
```

Note: Pico currently uses an OpenVM-compatible Rust CLI surface for loop1/loop2 orchestration, but its
backend replay/injection path is still partial (not yet equivalent to OpenVM backend completeness).
