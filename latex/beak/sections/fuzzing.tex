\section{Cross-zkVM Trace Semantics}\label{sec:trace-ir}

Although each zkVM encodes its execution trace in a radically different format (chip-level AIR rows in OpenVM, STARK columns in SP1, circuit tables in RISC Zero, lookup sequences in Jolt), all these systems must enforce the \emph{same} RISC-V semantic invariants. Register x0 must remain zero. Immediate values must decompose into correctly range-checked limbs. Memory timestamps must increase monotonically. When a backend's constraint system fails to enforce one of these invariants, a soundness bug exists.

This insight is the foundation of \tool's semantic model. Rather than analyzing each backend's constraint system directly---which would require six separate analyses---we define a common vocabulary of \emph{semantic categories}: named classes of constraint-correctness concerns where bugs cluster. Each category is a predicate on trace steps that identifies when a specific invariant-critical condition is exercised.

\subsection{Semantic Categories}\label{sec:semantic-model}

\paragraph{Running example}
Consider \icode{addi x1, x0, -1} executed on OpenVM. The ALU chip decomposes the 12-bit immediate ($-1$, encoded as \icode{0xFFF}) into byte-sized limbs for constraint evaluation over a finite field. At this trace step, \tool evaluates the \icode{alu.imm\_limb} category predicate, which checks whether the immediate value crosses a limb boundary. The same predicate applies identically when SP1 or any other backend processes the same instruction; categories are defined on backend-agnostic trace-step properties, abstracting away how each backend internally represents the decomposition.

\paragraph{Formal definition}
A trace step $s \in \mathit{Steps}(x)$ records the step index, instruction fields, and computed values (register state, immediate, memory address, etc.) during execution of input $x$ on a backend. A semantic category $c \in \mathcal{C}$ is associated with a predicate $\kappa_c : \mathit{Steps} \to \{0, 1\}$ that determines whether a trace step activates it. For example, the \icode{alu.imm\_limb} category activates when a step involves an immediate value that crosses a limb boundary (i.e., $\mathit{imm} \bmod 256 \in \{0, 255\}$). The \emph{category signature} for input $x$ is the set of all activated categories:
\begin{equation}\label{eq:signature}
\sigma(x) = \bigl\{c \in \mathcal{C} \;\big|\; \exists\, s \in \mathit{Steps}(x) : \kappa_c(s) = 1\bigr\}
\end{equation}
As we describe in \autoref{sec:fuzzing-framework}, signature novelty serves as the exploration feedback signal, \emph{and} each activated category simultaneously anchors a targeted witness injection.

\paragraph{Category derivation}
We derive the \tbd{39} categories from two complementary sources:

\begin{itemize}
    \item \textbf{Constraint categories (\tbd{32}).} Empirically derived from (1)~\tbd{25} professional security audit findings across 6 production zkVMs, (2)~\tbd{11} known bugs from prior dynamic testing~\cite{arguzz}, and (3)~the RISC-V RV32IM specification's edge cases. We mapped each known bug to the constraint component it violates and abstracted recurring patterns into named categories. This yields \tbd{10} category groups spanning the major functional components of a RISC-V zkVM (\autoref{tbl:categories}).

    \item \textbf{Resource categories (\tbd{7}).} Structurally derived from the $2^n$-sized data structures mandated by STARK arithmetization. Every STARK-based zkVM pads its execution trace to the next power of two; similarly, segment tables, RAM/ROM regions, lookup accumulators, commitment vectors, and range-check tables are all $2^n$-sized due to the FFT/NTT evaluation domain requirement. This creates \emph{structural invariant-critical conditions} at each $2^n$ transition---crossing a power-of-two threshold forces a backend to reallocate, resize, or restructure its arithmetic tables, stressing constraint logic that handles these transitions. Unlike the constraint categories (which are empirical), the \tbd{7} resource categories are an exhaustive enumeration of these $2^n$-sized structures (\autoref{tbl:resource-categories}).
\end{itemize}

As validation, all \tbd{6} zero-day vulnerabilities \tool discovered map to existing categories; no new categories were needed (\autoref{sec:eval-rq3}).

\paragraph{Category completeness and extensibility}
The \tbd{39} categories combine empirical saturation with structural completeness. Empirical sufficiency of the \tbd{32} constraint categories is validated by \tbd{97\%} category activation on known bugs (\autoref{sec:eval-rq3}) and all \tbd{6} zero-days mapping to existing categories. The \tbd{7} resource categories are structurally complete: they enumerate all $2^n$-sized objects in STARK-based backends (trace rows, segments, memory, bytecode, lookups, commitments, range tables). The set is incrementally extensible: adding a category requires only a new predicate $\kappa_c$ on trace steps---no changes to the fuzzing loop, bandit, or witness injection. The \tbd{10} missed bugs (\autoref{sec:eval-threats}) point to cross-component algebraic interactions as the primary gap.

\autoref{tbl:categories} and \autoref{tbl:category-predicates} illustrate the model's operation. Beyond the motivating example (\autoref{sec:motivating-example}), the resource categories are particularly effective for Type~I bugs: \icode{resource.trace\_util} catches Jolt's RAM-size overflow at $2^k$ thresholds, and \icode{resource.memory\_footprint} catches Nexus's memory-size crash at a $2^k$ address threshold. \subsection{Formal Properties of the Semantic Model}\label{sec:formal-properties}

We formalize the properties that underpin the semantic model's detection guarantees and the complementary roles of the two detectors.

\begin{definition}[Semantic Gap]\label{def:semantic-gap}
Let $B$ be a zkVM backend with executor $E_B$ and constraint system $\mathcal{C}_B$ over field $\mathbb{F}_p$, let $O$ be the reference RISC-V oracle, and let $x$ be an input program. Write $r_t \in \mathbb{Z}_{2^{32}}^{32}$ for the register state after step $t$ and $w_t \in \mathbb{F}_p^m$ for the witness row at step $t$ (where $m$ is the trace width). A \emph{semantic gap} exists at instruction step $t$ of $x$ in $B$ if at least one of the following holds:
\begin{itemize}
    \item \textbf{Type~I (Divergence):} The executor computes a register state that differs from the oracle: $E_B(x, t) \neq O(x, t)$, i.e., $\exists\, j \in [32] : r^B_{t,j} \neq r^O_{t,j}$.
    \item \textbf{Type~II (Underconstraint):} The executor computes the correct state ($E_B(x, t) = O(x, t)$), but the constraint system admits an alternative witness $w' \neq w_t$ at step $t$ such that $\mathcal{C}_B(w') = \mathsf{accept}$ and $\mathit{decode}(w') \neq \mathit{decode}(w_t)$, where $\mathit{decode}: \mathbb{F}_p^m \to \mathbb{Z}_{2^{32}}^{32}$ extracts the register state encoded by a witness row.
\end{itemize}
\end{definition}

\noindent Type~I gaps arise from prover-side errors (the executor computes incorrectly); Type~II gaps arise from verifier-side errors (the executor is correct but the constraint system is too permissive). The $\mathit{decode}$ function is backend-specific---e.g., OpenVM extracts 32~field elements and reduces modulo $2^{32}$; Jolt reconstructs from lookup table indices---but the definition is parametric in this mapping. The two types require different detection mechanisms: Type~I via output comparison, Type~II via alternative-witness construction.

\paragraph{Dual-detector coverage characterization}
The unified loop runs two detectors on every evaluation. Their coverage properties with respect to Definition~\ref{def:semantic-gap} are as follows:

\begin{enumerate}
    \item \textbf{The differential detector covers Type~I gaps.} Register comparison detects all Type~I gaps whose divergence propagates to the final register state, by construction (comparison is exact). Type~I gaps that crash the executor are handled via assertion-bypass instrumentation (\autoref{sec:instrumentation}), which converts fatal assertions to logged warnings and allows execution to continue to a (corrupted) final state. On the benchmark, all crash-inducing bugs are detected through this mechanism.

    \item \textbf{The injection detector covers Type~II gaps within instrumentation reach.} Witness injection can detect Type~II gaps at any step $t$ for which a category activation exists at step $s$ such that $|s - t| \leq \delta$ (the injection search window, default $\delta = \tbd{64}$). The coverage boundary is twofold: the search window $\delta$ limits spatial reach, and the category model limits semantic reach---gaps at uninstrumented constraint components are invisible to injection.

    \item \textbf{Neither detector subsumes the other.} Type~I gaps (executor divergences) produce no alternative witness and thus cannot be detected by injection. Type~II gaps (correct executor, permissive constraints) produce no register mismatch and thus cannot be detected by differential comparison. This separation is structural: on the benchmark, of the \tbd{34} detected bugs, \tbd{13} are Type-I-only and \tbd{21} are Type-II-only (the \tbd{10} undetected bugs are classified in \autoref{sec:eval-threats}), confirming that the two detectors are orthogonal capabilities.\label{item:separation}
\end{enumerate}

\paragraph{Detector complementarity bound}\label{cor:complementarity}
On the benchmark of \tbd{44}~known bugs, removing the injection detector reduces \tool's recall from \tbd{77.3\%} (\tbd{34/44}) to at most \tbd{29.5\%} (\tbd{13/44}). This bound is structural---it holds regardless of time budget, seed corpus, or mutation strategy---because Type~II gaps produce no observable signal in differential comparison. This observation quantifies the precise contribution of witness injection and explains the performance gap between \tool and prior differential-testing approaches such as \arguzz (which operates exclusively as a differential detector).

\begin{proposition}[Category Separation]\label{prop:category-separation}
The \tbd{11} category groups partition the category space such that any single-instruction execution activates at most one category per group. This holds by construction: predicates within a group share a common instruction-class filter (e.g., all Decode predicates require a register-write step targeting \texttt{x0} or its variants), and each instruction produces at most one activation per group per step. Consequently, a single-instruction execution produces at most \tbd{11} category activations, and the reachable signature space for $n$-instruction inputs is bounded by $\prod_{g \in G} (|g| + 1)^n$, which is exponentially smaller than $2^{32n}$ for short programs.
\end{proposition}

\noindent This design invariant ensures that signatures are \emph{informative} (distinct signatures reflect genuinely different constraint behaviors) and that the reachable space is bounded: the benchmark produces fewer than \tbd{200} distinct signatures despite $2^{32} \approx 4 \times 10^9$ theoretical possibilities, so the novelty signal is well-founded.

\subsection{Backend Instrumentation}\label{sec:instrumentation}

\tool instruments each backend's trace-generation path via automated source patching in three passes: (1)~\textbf{infrastructure injection} adds a uniform category-evaluation API; (2)~\textbf{assertion bypass} replaces Rust \icode{panic!}/\icode{assert!} macros (identified by textual pattern matching on source code) with logged warnings, enabling execution of crash-inducing inputs---sandboxed execution with a watchdog mitigates the UB risk from bypassed assertions (rare: \tbd{3}/44 benchmark inputs); (3)~\textbf{category hooks} are inserted at each backend's constraint-component sites (ALU chips evaluate limb-decomposition predicates, memory chips evaluate address-alignment predicates, etc.).

The instrumentation is \emph{sound} (category evaluations faithfully reflect computed trace facts) but not \emph{complete} (new constraint components require new hooks). Effort ranges from ${\sim}\tbd{200}$ LOC (Nexus) to ${\sim}\tbd{600}$ (OpenVM); each backend exposes a uniform interface returning 32 registers and activated categories. \tool skips proof generation, reducing per-input evaluation from minutes to milliseconds. \autoref{tbl:backends} lists the six supported backends.
