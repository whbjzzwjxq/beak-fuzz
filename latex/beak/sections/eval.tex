\section{Evaluation}\label{sec:eval}

We evaluate \tool to answer the following research questions:
\begin{itemize}
    \item \textbf{RQ1 (Effectiveness):} How effective is \tool at discovering semantic gaps compared to state-of-the-art zkVM testing approaches?
    \item \textbf{RQ2 (Ablation):} What is the contribution of each key design component: category feedback, bandit-guided mutation, witness injection, and ISA-aware mutation?
    \item \textbf{RQ3 (Generalizability):} How well does the semantic model generalize across diverse zkVM architectures?
    \item \textbf{RQ4 (Zero-Days):} Can \tool discover previously unknown vulnerabilities in production-grade zkVMs?
\end{itemize}

\subsection{Experimental Setup}\label{sec:eval-setup}

\paragraph{Target zkVMs}
We evaluate \tool on six production zkVM systems: OpenVM, SP1, RISC Zero, Jolt, Nexus, and Pico. For each system, we test against one or more pinned commit snapshots to ensure reproducibility. \autoref{tbl:backends} in \autoref{sec:instrumentation} lists the proving system and number of snapshots per backend.

\paragraph{Seed corpus}
The initial seed corpus consists of \tbd{2,172} RISC-V RV32IM instruction sequences extracted from the official RISC-V test suite (\icode{riscv-tests}). Each seed is a sequence of 32-bit instruction words (up to \tbd{256} instructions) covering all RV32IM operations, including edge cases such as division by zero, signed overflow, and misaligned memory access patterns. The fuzzing loop (\autoref{alg:fuzzing}) mutates these seeds via the UCB1 bandit, generating an enriched corpus of novel inputs that activate previously unseen category signatures.

\paragraph{Baselines}
We compare \tool against:
\begin{itemize}
    \item \textbf{\arguzz}~\cite{arguzz}: a state-of-the-art dynamic testing framework for zkVMs that combines metamorphic testing with fault injection.
    \item \textbf{Random}: a baseline fuzzer that uses uniform random byte-level mutation without semantic feedback, category guidance, or ISA-aware operators.
\end{itemize}

\paragraph{Configuration}
All experiments are conducted on a machine with an AMD Ryzen 9 5950X CPU (16 cores) and 64~GB RAM, running Ubuntu 20.04. The fuzzing timeout is set to \tbd{6} hours per backend. \tool uses the default configuration: UCB1 exploration constant $\alpha = \tbd{1.5}$, epsilon $\varepsilon = \tbd{0.05}$, witness injection search window of \tbd{16} steps before and \tbd{64} steps after the anchor, and a maximum of \tbd{64} injection trials per category.

\paragraph{Metrics}
We measure four metrics: (1)~\textbf{unique bugs found}, the count of distinct semantic divergences and underconstrained candidates; (2)~\textbf{unique category signatures}, the number of distinct signature combinations discovered; (3)~\textbf{time to first bug (TTF)}, the latency from fuzzing start to the first confirmed bug; and (4)~\textbf{semantic category coverage}, the fraction of the \tbd{39} categories activated at least once.

\subsection{RQ1: Bug Detection Effectiveness}\label{sec:eval-rq1}

All \tbd{44} bugs are included in the benchmark; the \tbd{6}~zero-days are included because they are independently verifiable ground-truth bugs (confirmed and patched upstream), but we additionally report the conservative recall on the \tbd{38}~non-self-discovered bugs (\tbd{28/38}, \tbd{73.7\%}) for transparency. For each bug, we determine whether each tool can detect it, either through register-level divergence (Type~I) or underconstrained witness acceptance (Type~II). \autoref{tbl:effectiveness} presents the per-backend recall.

\paragraph{Witness injection is the dominant component}
The injection-detector ablation admits a \emph{structural bound} that holds regardless of time budget or seed corpus. Of the \tbd{44} benchmark bugs, \tbd{31} are verifier-side (the executor computes the correct answer, but the constraint system admits an alternative witness). These bugs produce no register mismatch and are invisible to the differential detector. Of the \tbd{34} bugs \tool detects, \tbd{21} (\tbd{62\%}) are verifier-side; without witness injection, recall drops from \tbd{77.3\%} to at most \tbd{29.5\%} (the \tbd{13} Type~I divergence bugs). This bound also explains the gap with \arguzz: of the \tbd{23} bugs \tool detects but \arguzz misses, \tbd{21} are verifier-side, unreachable by any differential-testing oracle.

\paragraph{Other components}
ISA-aware mutation ensures encoding validity: random 32-bit mutations produce decodable RV32IM instructions with probability $< \tbd{2^{-7}}$, so byte-level havoc spends most of the budget on decoder-rejected inputs. Category feedback provides structured exploration of the \tbd{39}-dimensional semantic space, distinguishing rare invariant activations from common ones. The UCB1 bandit adapts mutation allocation to each backend's constraint structure (e.g., favoring constant mutation on backends with complex limb logic), primarily affecting efficiency rather than reachability.

\paragraph{Case study: x0 register overwrite (ZD-01/02/03)}
The same vulnerability class exists independently in three zkVMs: RISC Zero allowed an ecall to write to x0; OpenVM lacked a circuit-layer zero-register constraint; Pico aliased registers with memory, so \icode{sw} to address~0 overwrites x0. \tool detects all three via the \icode{decode.zero\_reg} category---a single category catches the same concern across three radically different architectures.

\paragraph{Case study: \icode{is\_real} bypass (ZD-04) and timestamp wrap (ZD-06)}
ZD-04: Pico's \icode{MemoryLocalChip} omits the boolean constraint on the \icode{is\_real} lookup multiplicity; the \icode{lookup.boolean\_mult} category anchors injection of a non-boolean value, and the circuit accepts. ZD-06: Pico's timestamp monotonicity check wraps modulo $p \approx 2^{31}$; the \icode{time.boundary\_origin} category anchors injection of a near-$p$ timestamp. Both are Type~II---invisible to differential testing.

\paragraph{Security impact}
All \tbd{4} critical bugs enable forging proofs for incorrect RISC-V execution. The x0 vulnerability is particularly noteworthy: the same ISA-level invariant was independently violated in three unrelated codebases.

\subsection{Discussion and Threats to Validity}\label{sec:eval-threats}

\paragraph{Precision}
The differential detector's false positives arise only from oracle bugs---unlikely given our validated \icode{riscv-tests} reference. The injection detector flags a candidate only when the constraint system \emph{accepts} an injected alternative witness, producing a constructive proof of underconstraint. Rare semantically-equivalent alternatives (valid alternative decompositions) are filtered by post-injection output comparison. \paragraph{Validity}
All tools share the same seed corpus (\tbd{2,172} \icode{riscv-tests} sequences), hardware, and \tbd{6}-hour budget. We define ``bug'' as a register mismatch or underconstrained witness confirmed by manual inspection; zero-day confirmations come from upstream teams. The \tbd{44}-bug benchmark is curated from four independent sources, reducing bias. The six backends span four proving architectures (STARK, IVC, lookup-based, modular chip AIR). The current results use fixed seeds; multi-run validation with confidence intervals~\cite{klees2018evaluating} would strengthen the evaluation, though \tool's structurally-determined feedback signal is less seed-sensitive than coverage-guided fuzzing.

\paragraph{Limitations}
The \tbd{10} missed bugs require \emph{cross-component algebraic reasoning}: LogUp multiplicity wraparound (\tbd{2}~OpenVM, \tbd{1}~SP1), interaction-digest collisions (\tbd{1}~OpenVM), non-canonical witnesses (\tbd{3}~RISC~Zero), and opcode-selector ambiguities (\tbd{2}~Pico, \tbd{1}~SP1). These exploit global protocol-level invariants rather than per-instruction invariant-critical conditions. In practice, effective bug-finding inputs are short (\tbd{3--12} instructions); scalability is bounded by trace-generation cost and diminishing signature novelty for longer programs.
